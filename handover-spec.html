01배경과 목적

현재 ESG 중장기전략 관리는 부서별로 분기 PPT 양식을 작성해 제출하고, ESG 사무국이 이를 수작업으로 취합하는 방식입니다.

이 방식의 문제는 세 가지입니다. 첫째, 전사 달성률과 팀 간 비교를 실시간으로 볼 수 없습니다. 둘째, 지연이 발생한 과제를 분기 마감 이후에야 발견합니다. 셋째, 달성률이 담당자의 주관 판단이어서 팀마다 후하거나 박해 비교 자체가 무의미해집니다.

이 시스템은 계획 항목 단위의 체크로 달성률을 자동 산정해 세 문제를 함께 해결합니다. 담당자가 세부 계획 항목의 상태만 갱신하면 근거가 명확한 숫자가 나오고, 기간경과 대비 지연 여부가 자동 판정됩니다.

기존 보고 양식의 구조 보존

담당자가 이미 사용하던 분기 보고 양식의 5개 블록을 화면에 그대로 재현하는 것이 요건입니다. 학습 비용이 없다는 점이 이 시스템의 핵심 강점이므로, 임의로 재구성하지 않아야 합니다.

02사용자와 권한

세 종류의 사용자가 있고, 권한은 서버가 판정해야 합니다.

사용자규모(예상)할 수 있는 일
ESG 사무국1–2명전 과제 등록·수정·삭제, 팀 마스터 관리, CSV 추출
현업부서 담당자부서당 1–2명과제 등록·수정, 계획 항목 상태 변경, 기간 실적 입력

R-1인증은 사내 계정에 위임한다

별도 회원가입·비밀번호 관리를 만들지 않습니다. 사내 SSO 또는 그룹웨어 계정 세션으로 로그인 상태를 판정합니다.

R-2쓰기 권한은 서버가 차단한다

열람자에게 입력 UI를 숨기는 것만으로는 부족합니다. 모든 쓰기 API가 서버에서 권한을 재확인해 거절해야 합니다. 프로토타입 단계에서 열람자가 다른 팀 과제를 삭제할 수 있었던 것이 이 요건의 배경입니다.

R-3화면은 권한에 따라 달라진다

열람자에게는 등록·수정·삭제·실적 입력·항목 체크 UI가 아예 표시되지 않아야 합니다. GET /api/session이 내려주는 권한 등급으로 프론트엔드가 분기합니다(§6).

R-4담당자는 자기 팀 과제만 수정권장 · 선택

사내 계정으로 소속 팀을 알 수 있다면, 담당자의 쓰기 범위를 본인 팀 과제로 제한하는 것이 안전합니다. 프로토타입에서는 사용자 신원을 알 수 없어 구현하지 못했던 항목입니다. ESG 사무국은 예외로 전 팀을 수정할 수 있어야 합니다(대리 입력·정정 필요).

R-12내비게이션은 좌측 1단 + 상단 하위탭 2단이다

좌측 아이콘 레일이 주 화면(대시보드 / 과제 목록 / 사업장·팀 현황 / 전략 등록)을 고르고, 상단 알약형 탭은 그 화면의 하위 섹션을 고릅니다. 같은 항목을 양쪽에 중복 배치하지 마십시오.

대시보드 하위탭은 전체화면 · 중장기전략 로드맵 · 조치 필요 · 팀별 달성률이며, 탭에 해당 건수를 함께 표시합니다. 각 하위 화면은 요약 통계 박스 + 상세 목록 형태로 펼칩니다 — 예: 조치 필요 화면은 위험·지연·미제출·지연사유 미기재 건수를 상단에 놓고, 각 과제 카드에 달성/기대 갭과 지연 사유·Catch-up Plan 본문을 함께 보여줍니다. 과제 목록은 ESG 영역별(전체/환경/사회/지배구조), 사업장·팀 현황은 사업장별/팀 전체를 하위탭으로 씁니다.

중장기전략 로드맵 (대시보드 상단)

R-10로드맵은 분기 단위 간트 그리드로 그린다

행은 실행과제(왼쪽에 과제명·팀·담당자 카드를 고정 표시), 열은 분기입니다. 열 범위는 전체 과제의 추진기간을 덮되 현재 분기가 항상 포함되어야 하며, 가로 스크롤로 처리하고 최초 표시 시 현재 분기가 보이는 위치로 스크롤합니다.

과제마다 start_year~end_year 구간에 막대를 그립니다. 막대 색은 ESG 영역(환경/사회/지배구조 3색), 막대 아래를 가로지르는 얇은 띠가 현재 달성률, 막대 오른쪽 끝의 흰 칩이 이행 상태와 달성률입니다. 색으로 영역을, 칩으로 상태를 나누어 두 정보가 섞이지 않게 한 구성이므로 유지하십시오.

경과된 분기 열은 사선 해칭으로, 현재 분기는 열 머리를 강조하고 세로 점선을 그려 구분합니다. 행 정렬은 위험 → 지연 → 미착수 → 정상 → 완료 순으로, 조치가 필요한 과제가 위에 오게 합니다.

담당자 입력 부담이 설계 제약입니다

담당자는 분기에 한 번 들어오는 사용자입니다. 한 과제 입력이 5분을 넘기면 제출률이 떨어집니다. 실적 입력 폼에서 계획 항목 체크와 실적 서술을 한 화면에서 처리하고, 체크하는 즉시 계산된 달성률이 화면에 보이도록 설계되어 있습니다. 이 구조를 여러 단계로 쪼개지 마십시오.

04데이터 모델

테이블 4개입니다. 아래 DDL은 표준 SQL로 작성했으며, 자료형은 사내 DB에 맞게 조정하십시오.

-- 0. 사업장 마스터. 본사 / 포항공장 / 창원공장 / 군산공장 / 순천공장
CREATE TABLE esg_site (
  site_id      INTEGER      PRIMARY KEY,
  name         VARCHAR(30)  NOT NULL UNIQUE,
  sort_order   INTEGER      NULL,                 -- 화면 표시 순서 (본사 우선)
  created_at   TIMESTAMP    NOT NULL,
  updated_at   TIMESTAMP    NOT NULL
);

-- 1. 팀 마스터. 팀은 반드시 한 사업장에 속한다 (R-11).
CREATE TABLE esg_team (
  team_id      INTEGER      PRIMARY KEY,          -- MSSQL: IDENTITY / MySQL: AUTO_INCREMENT
  site_id      INTEGER      NOT NULL REFERENCES esg_site(site_id),
  name         VARCHAR(40)  NOT NULL UNIQUE,      -- 유니크 제약 필수 (R-5)
  sort_order   INTEGER      NULL,
  created_at   TIMESTAMP    NOT NULL,
  updated_at   TIMESTAMP    NOT NULL
);

-- 2. 실행과제
CREATE TABLE esg_strategy (
  strategy_id  INTEGER      PRIMARY KEY,
  title        VARCHAR(200) NOT NULL,
  esg_category CHAR(1)      NOT NULL CHECK (esg_category IN ('E','S','G')),
  team_id      INTEGER      NOT NULL REFERENCES esg_team(team_id),
  owner_name   VARCHAR(40)  NULL,                 -- 실무 담당자 표기용
  start_year   INTEGER      NOT NULL,
  end_year     INTEGER      NOT NULL,
  priority     VARCHAR(4)   NULL CHECK (priority IN ('상','중','하')),
  purpose      VARCHAR(2000) NULL,                -- 추진 배경·목적
  kpi_name     VARCHAR(100) NULL,
  kpi_unit     VARCHAR(20)  NULL,
  kpi_base     DECIMAL(18,4) NULL,                -- 기준값(Baseline)
  kpi_target   DECIMAL(18,4) NULL,                -- 목표값
  created_by   VARCHAR(40)  NOT NULL,
  created_at   TIMESTAMP    NOT NULL,
  updated_at   TIMESTAMP    NOT NULL,
  CHECK (end_year >= start_year)
);

-- 3. 계획 항목. 달성률의 근거이므로 반드시 별도 행으로 관리한다.
CREATE TABLE esg_strategy_plan (
  plan_id      INTEGER      PRIMARY KEY,
  strategy_id  INTEGER      NOT NULL REFERENCES esg_strategy(strategy_id) ON DELETE CASCADE,
  seq          INTEGER      NOT NULL,             -- 화면 표시 순서
  plan_text    VARCHAR(500) NOT NULL,
  status       VARCHAR(5)   NOT NULL DEFAULT 'todo'
                            CHECK (status IN ('todo','doing','done')),
  updated_by   VARCHAR(40)  NULL,
  updated_at   TIMESTAMP    NOT NULL,
  UNIQUE (strategy_id, seq)
);

-- 4. 기간별 실적. 분기는 필수 보고, 월은 선택 기록.
CREATE TABLE esg_progress (
  progress_id  INTEGER      PRIMARY KEY,
  strategy_id  INTEGER      NOT NULL REFERENCES esg_strategy(strategy_id) ON DELETE CASCADE,
  period_type  CHAR(1)      NOT NULL CHECK (period_type IN ('Q','M')),
  period_key   VARCHAR(7)   NOT NULL,             -- 'YYYY-Qn' 또는 'YYYY-MM'
  progress_pct INTEGER      NOT NULL,             -- 제출 시점 달성률 스냅샷 (0~100)
  achievement  VARCHAR(4000) NOT NULL,            -- 해당 기간 실적 서술
  kpi_actual   DECIMAL(18,4) NULL,
  delay_reason VARCHAR(4000) NULL,
  catchup_plan VARCHAR(4000) NULL,
  author_name  VARCHAR(40)  NOT NULL,
  author_team  VARCHAR(40)  NOT NULL,
  updated_at   TIMESTAMP    NOT NULL,
  UNIQUE (strategy_id, period_key)                -- 같은 기간 재제출은 덮어쓰기(UPSERT)
);

CREATE INDEX ix_strategy_team   ON esg_strategy(team_id);
CREATE INDEX ix_plan_strategy   ON esg_strategy_plan(strategy_id);
CREATE INDEX ix_prog_strategy   ON esg_progress(strategy_id);
CREATE INDEX ix_prog_period     ON esg_progress(period_key);

DDL — 표준 SQL. IDENTITY/AUTO_INCREMENT, TIMESTAMP 자료형, 한글 CHECK 제약은 사내 DB 문법에 맞게 조정

R-5팀 이름은 유니크해야 한다

"품질경영팀"과 "품질경영 팀"이 서로 다른 팀으로 들어가면 팀별 달성률이 쪼개져 대시보드 자체가 신뢰를 잃습니다. DB 유니크 제약과 함께, 저장 전 공백·하이픈·언더바·중점·마침표·괄호를 제거하고 소문자화한 값으로 중복을 검사하십시오.

R-6달성률은 저장하지 않고 계산한다

esg_strategy에 달성률 컬럼을 두지 마십시오. 현재 달성률은 항상 esg_strategy_plan에서 실시간 계산합니다(§5 R-7). esg_progress.progress_pct는 제출 시점의 스냅샷으로, 추이 조회 전용이며 현재값으로 쓰지 않습니다.

R-7과제가 남은 팀은 삭제할 수 없다

외래키 제약으로 막고, API도 삭제 전 과제 수를 확인해 거절하십시오. 소속 팀이 남은 사업장도 같습니다.

R-11조직은 사업장 → 팀 2단 계층이다

과제는 team_id만 들고, 사업장은 팀을 통해 파생시킵니다(esg_team.site_id). 과제에 site_id를 중복 저장하지 마십시오 — 팀의 사업장이 바뀌면 두 값이 어긋납니다.

등록 화면에서는 사업장을 먼저 고르면 그 사업장의 팀만 선택 목록에 나옵니다. 집계는 팀 → 사업장 → 전사 3단으로 올라가며, 각 단계 모두 단순 평균입니다(§5).

초기 사업장: 본사, 포항공장, 창원공장, 군산공장, 순천공장. 사업장 추가·변경은 사무국이 관리 화면에서 처리합니다.

05산정 규칙

이 절이 이 문서에서 가장 중요합니다. 숫자가 달라지면 시스템의 신뢰가 무너지므로, 아래 정의를 그대로 구현하십시오. 프로토타입에서 검증된 규칙입니다.

달성률 (현재값)

달성률(%) = ROUND( (완료항목수 + 진행중항목수 × 0.5) / 전체항목수 × 100 )
전체항목수 = 0 인 경우 → 0

진행중을 0.5로 세는 것이 핵심입니다. 완료만 인정하면 보고서를 3개월 붙잡고 있는 동안 내내 0%로 잡히다가 어느 분기에 갑자기 튀어오르는 계단형이 되고, 담당자는 "일한 것이 반영되지 않는다"고 느낍니다. 반대로 항목마다 %를 직접 입력하게 하면 결국 주관 판단으로 되돌아갑니다.

기간경과 기대치

분기인덱스(period) = 연도 × 4 + (분기 − 1)          -- 예: 2026-Q3 → 8106

총분기수   = (완료연도 − 시작연도 + 1) × 4
경과분기수 = 분기인덱스(현재분기) − 시작연도 × 4 + 1
기대치(%)  = CLAMP( ROUND(경과분기수 / 총분기수 × 100), 0, 100 )

"2025~2027 과제가 2026년 3분기에 45%"라는 숫자만으로는 정상인지 알 수 없습니다. 이 기대치가 기준선 역할을 합니다.

이행 상태 판정

상태조건우선순위
완료달성률 ≥ 1001
미착수달성률 = 0 이고 실적 이력이 하나도 없음2
정상(달성률 − 기대치) ≥ −5 %p3
지연(달성률 − 기대치) ≥ −20 %p4
위험그 미만5

위에서부터 먼저 맞는 조건을 적용합니다.

KPI 달성률

IF 기준값 존재 AND 기준값 ≠ 목표값 THEN
    ROUND( (실적 − 기준값) / (목표값 − 기준값) × 100 )
ELSE IF 목표값 ≠ 0 THEN
    ROUND( 실적 / 목표값 × 100 )
ELSE
    표시하지 않음 (N/A)
감축형 지표 주의

재해율 0.82 → 0, 배출 원단위 12.4 → 8.7 처럼 낮출수록 좋은 지표가 ESG에는 많습니다. 실적 ÷ 목표로 단순 계산하면 무의미한 값이 나오거나 0으로 나누는 오류가 발생합니다. 기준값 대비 방식이 이를 해결합니다.

입력 주기와 미제출 판정

R-8분기는 필수, 월은 선택

분기 마감만 의무이고, 그 사이에 진전이 생기면 월 단위로도 기록할 수 있습니다. 미제출 독촉과 팀 집계는 분기 행(period_type = 'Q')만 기준으로 판정하며, 월 행은 세지 않습니다. 월 의무화는 입력 횟수를 3배로 만들고 변화 없는 과제에 "동일"을 반복 입력하게 해 제출률을 떨어뜨립니다.

미제출 과제 = 현재 분기의 period_key 행이 없는 과제
당분기 제출률(%) = ROUND(제출 과제 수 / 전체 과제 수 × 100)
R-9기대치 미달 시 지연 사유 필수

조건: 달성률 < 기대치 − 5 이고 달성률 < 100 인 경우, delay_reason이 비어 있으면 저장을 거절합니다. 원본 양식의 "(해당시) 계획대비 지연 사유" 블록이 실제 보고에서 비어 오는 것을 방지하는 장치입니다. 서버에서도 검증하십시오.

화면 확인이 필요하시면 ESG 사무국에 요청하십시오. 소스 HTML 파일은 전달 가능하며, 로컬에서 파일을 열면 레이아웃과 상호작용을 확인할 수 있습니다(데이터 연결은 되지 않음).

09회신 요청 사항

아래 6개 항목의 답을 받으면 그에 맞춘 DB 스키마와 백엔드 코드를 준비할 수 있습니다. 환경을 모르는 상태에서 작성하면 버리는 작업이 되므로, 이 회신이 다음 단계의 선행 조건입니다.

IT부서 회신 요청 — 6항
  1. Q1
    서버 환경은 무엇입니까?
    서버 OS, 웹서버(IIS / nginx / Apache), 실행 런타임(.NET / Node.js / PHP / Java 등)
  2. Q2
    데이터베이스 종류와 버전은 무엇입니까?
    MSSQL / MySQL / MariaDB / PostgreSQL / Oracle. §4 DDL의 자료형과 시퀀스 방식이 여기서 결정됩니다
  3. Q3
    사내 계정 인증을 연동할 수 있습니까?
    SSO 또는 그룹웨어 세션. 사용자 식별자·이름·소속 팀을 애플리케이션이 받을 수 있는지가 핵심입니다(R-1, R-3)
  4. Q4
    권한 등급을 어떻게 부여합니까?
    담당자(editor)와 열람자(viewer)를 구분할 방법 — 인사시스템 직무 정보, 별도 권한 테이블, 사무국 수동 지정 중 무엇이 가능한지. R-4(자기 팀만 수정) 구현 여부도 여기에 달려 있습니다
  5. Q5
    팀 정보를 인사시스템에서 가져올 수 있습니까?
    가능하다면 esg_team 마스터와 팀 관리 화면이 불필요해지고, 조직 개편 시 자동 반영됩니다. 불가능하면 §4 설계대로 별도 관리합니다
  6. Q6
    접속 범위와 예상 일정은 어떻게 됩니까?
    사내망 전용인지 외부(재택) 접속이 필요한지, 그리고 구축 가능 시점. ESG 사무국은 분기 마감 주기에 맞춰 배포 시점을 잡아야 합니다
Q3~Q5가 안 되는 경우

사내 계정 연동이 불가능하다면 권한 구분을 포기하거나(전원 편집 가능), 사무국 전용 도구로 범위를 축소하는 선택이 됩니다. 그 경우 요건을 다시 잡아야 하므로, 불가능하다는 답도 그대로 회신해 주시면 됩니다.

이 문서는 ESG 사무국이 프로토타입 검증을 마친 뒤 작성한 이관 요청서입니다. §5 산정 규칙과 §2 권한 요건은 실제 사용 과정에서 결정된 사항이므로 임의로 변경하지 마시고, 조정이 필요하면 ESG 사무국과 협의해 주십시오. 문서 작성일 2026-09-10.
